# Talentra Security Architecture, Threat Model & PII Protection Note
**Docket Reference**: Milestone 22 (Backlogs B75–B79) & Milestone 23 (Backlog B81)

## 1. PII Classification & Handling Strategy Across Modules (B75–B77)

The platform classifies data into four tiers: **`Public`**, **`Internal`**, **`Personal`**, and **`Sensitive`**. The protection mechanisms applied across each subsystem are documented below:

### A. Administration, Organisation & Gig Marketplace (B75)
* **National & Corporate Tax Identifiers (CIN, GSTIN, EIN)**:
  * *Policy*: Cleartext corporate registration and tax numbers are never exposed in public profile views.
  * *Storage Mechanism*: Stored as masked strings (`27AAAAA****A1Z5`) for human inspection, paired with an HMAC-SHA256 salted hash (`identifier_hash`) for zero-knowledge collision checks and deduplication.
* **Candidate E.164 Contact Records**:
  * *Policy*: Phone numbers and direct email addresses are strictly masked (`+91 98****3210`, `a***v@example.com`) during exploratory searches.
  * *De-masking*: Direct contact details are only unveiled to recruiters upon explicit candidate profile download accompanied by wallet credit deduction (`candidate_profile_download_history`).

### B. Licences, Sourcing & Subscriptions (B76)
* **Payment References & Financial Tokens**:
  * *Zero Cardholder Data Footprint*: Raw credit card numbers, CVVs, and bank account credentials NEVER enter or touch Talentra servers or database storage (strictly adhering to PCI-DSS Level 1 compliance).
  * *Tokenization*: Talentra stores only third-party gateway reference identifiers (`gateway_order_reference_id`, `gateway_refund_reference_id`) generated by Stripe/Razorpay.
* **User Authentication Credentials**:
  * *Hashing Standard*: Passwords hashed using **Argon2id** (memory cost 64MB, time cost 3 iterations, parallelism 4) with unique 128-bit cryptographically random salts per user. Plaintext passwords or legacy MD5/SHA-1 hashes are prohibited.
  * *Session Tokens*: Stored as SHA-256 digests (`session_token_hash`).

### C. Notifications, Community & Analytics Marts (B77)
* **Outbox Notification Queues**:
  * Message payloads (`notification_delivery.payload_json`) retain operational data for a maximum 7-day delivery buffer. Identifiable message bodies are purged post-delivery, retaining only the dispatch audit event.
* **Dimensional Analytics Isolation (Kimball Star Schema)**:
  * Dimensions (`dim_candidate`, `dim_job`, `dim_organisation`) and event facts (`fact_application_event`, `fact_wallet_transaction`) are completely scrubbed of candidate direct contact identifiers (names, emails, phone numbers, exact birth dates).
  * Candidate identity is represented solely through surrogate integer keys and coarse demographic bands (`experience_tier_code`, `city_name`).

## 2. Comprehensive Threat Model & Defense Matrix (B78)

We applied the **STRIDE** methodology (Spoofing, Tampering, Repudiation, Information Disclosure, Denial of Service, Elevation of Privilege) to evaluate threats against Talentra’s database architecture:

| STRIDE Threat Category | Potential Attack Scenario | Talentra Database Architectural Control |
| :--- | :--- | :--- |
| **Spoofing Identity** | An unauthorized actor fabricates a session token or impersonates an enterprise recruiter. | Argon2id salted credentials, SHA-256 session token hashing, hardware device fingerprint binding (`user_device`), and mandatory session expiry timestamps. |
| **Tampering with Data** | A rogue admin or SQL injection attempts to adjust wallet balances or delete candidate audit trails. | Strict append-only triggers (`trg_audit_log_prevent_update`, `trg_wallet_transaction_prevent_update`) block `UPDATE` and `DELETE` commands at the storage engine level. |
| **Repudiation** | An employer disputes initiating a bulk outreach campaign or downloading candidate resumes. | Immutable event logs in `audit_log`, `bulk_outreach_batch`, and `candidate_profile_download_history` record actor ID, client IP, user agent, and timestamp. |
| **Information Disclosure** | Competitors or blocked employers attempt to discover candidates who have blocked them. | Dynamic privacy blocking enforcement embedded in database views (`v_candidate_discovery`) and query sub-filters (`NOT EXISTS in privacy_block_entry`). |
| **Denial of Service** | Credential stuffing, concurrent session flooding, or unindexed 100M-row table scans. | Database-enforced session limits inside `sp_authenticate_and_open_session`, rate-limiting tracking in `login_attempt_history`, and composite B+Tree indexing. |
| **Elevation of Privilege** | An external agency recruiter attempts to read or mutate private requisitions of other employers. | Strict tenant isolation via `recruiter_assignment` and `v_recruiter_job_feed`; candidate blocking rules prevent unauthorized profile access. |

## 3. Access & Audit Verification Test Results (B79)

We executed targeted unit validation tests against the active MySQL 8.0 schema to verify non-functional security constraints:

### Test Case 1: Candidate Privacy Blocking Enforcement
* **Scenario**: Candidate #1 creates an active privacy block entry against Employer Organization #1.
* **Test Query**: Recruiter belonging to Org #1 executes candidate search (`v_candidate_discovery`).
* **Result**: **PASS**. Candidate #1 is completely omitted from the result set, eliminating unauthorized surveillance.

### Test Case 2: Recruiter Company Isolation
* **Scenario**: Recruiter User #2 (mapped strictly to Organisation #2) queries job requisitions.
* **Test Query**: Recruiter invokes `v_recruiter_job_feed`.
* **Result**: **PASS**. Zero job requisitions from Organisation #1 or other companies are returned.

### Test Case 3: Immutable Append-Only Ledger Protection
* **Scenario**: An attacker issues `UPDATE wallet_transaction SET transaction_amount = 999999 WHERE id = 1;` or `DELETE FROM audit_log WHERE id = 1;`.
* **Result**: **PASS**. Blocked by database triggers with SQLSTATE `45000` (`Financial Integrity Violation: wallet_transaction is an append-only ledger`).

### Test Case 4: Hardware Device & Session Limit Concurrency Enforcement
* **Scenario**: A user under an enterprise licence allowing 2 devices attempts to authenticate a 3rd concurrent active session.
* **Result**: **PASS**. Stored procedure `sp_authenticate_and_open_session` returns `DEVICE_LIMIT_EXCEEDED`, rejects session creation, and writes a security violation record to `audit_log`.
